## 0. 结论摘要

1. 手头 10 个可测样本在 Windows / LibRaw 0.22.2 / rawler 0.8.0 上：**7 个走 RAW 路径解码成功且无色条**；**3 个 Flextight FFF 在 RAW 后端全部失败（`-2 Unsupported` / `No decoder found`）——但它们不归 RAW 管辖**（更正见顶部），应用分流后走 TIFF 解码：2 个经生产路径全幅解码成功，`无法反相.fff` 在导出全幅路径仍超 512 MB 条带缓冲上限（§3.1）。
2. 负责人点名的三份样本（尼康 Z f HE、Z f 无损、哈苏 X2D 3FR）**均不在盘上**，GitHub #6 报障用户也未附文件；三列以「等待样本」入表，不用合成数据顶替。
3. 解码失败清单的现状：GitHub issues 里唯一解码失败报告是 **#6（尼康 Z f 固件 3.00，HE\* 即 NEFCompression=14，横向彩条+下半屏纯绿）**；#5（色域溢出）、#7（UI bug）与解码无关。盘上另有负责人早期标注的两个失败文件（无法反相.fff、FC导出tif导入失败.tif），前者**更正（Phase 3.1）：属 TIFF 流式解码路径的条带体积失败（§3.1），不是 RAW 解码层失败**；后者是 TIFF 导入路径（非 RAW 解码层，归其他阶段）。
4. M3 方案：**两平台统一到 LibRaw 0.22.2**。macOS 侧 vendor 一份 rsraw-sys 构建系统 + LibRaw 0.22.2 源码（源码编译），Windows 侧 rawlib 0.7.1 预编译库不动——Windows 解码输出字节级不变，A/B 只需证明「无回归」；变化全部落在 macOS 侧。`RAW_DECODE_VERSION` 12 → 13。

## 1. 测量方法

- **Harness**：`src/raw_backend.rs` 的 `decode_matrix_diagnostic`（`#[ignore]` 手动诊断测试，写法沿 `export_preview_parity_diagnostic`）。每个样本走两条双源入口：`decode_raw_mosaic`（黑电平/白电平/机型/解码器身份）与 `extract_camera_rgb_with_policy`（生产 `DecodeOptions`，仅 half_size 压内存——矩阵值、黑电平、成败均与 half_size无关）。
- **应用路由列（Phase 3.1 新增）**：每行记录 `app_route`——用**生产分流谓词**（`commands::decode_route_for_diagnostic`，与 `decode_image_buffer` 同一套判定：`is_scanner_fff_tiff` → `scanner-fff-stream`，直读图片扩展名 → `direct-image`，其余 → `raw`）标注应用实际走的路径；分流到非 RAW 路径的样本，再用该路径的**生产入口**（`decode_routed_for_diagnostic` = `decode_image_buffer(ExportFull)`）实测成败与尺寸。RAW 后端列因此只回答「后端能不能解」，应用路由列回答「应用实际怎么办」——两者不再混为一谈。
- **解码结果判定**：两入口的 Ok/Err 原样记录；像素来源由 mosaic 的 `decoder_source` 标注（libraw 直解 / rawler M2 回退）。
- **色条判定（客观阈值法）**：对解码 RGB（16-bit）做行均值与列均值剖面，取相邻行的**通道差分步长** `max(|ΔR−ΔG|, |ΔG−ΔB|, |ΔR−ΔB|)`。亮度阶跃（地平线、印样框格）三通道同动、差分相消；解码彩条通道间发散、差分残留。步长 > `20 × p95 + 2% 满量程` 记一次「色度步进」，**≥4 次判色条**（单次可能是真实场景色边界）。半幅均值与绿通道占比一并记录（#6 的「下半屏纯绿」特征）。
- **原始数据**：`target/diag-decode-matrix/matrix-before.json`（诊断产物不入库）。
- **复现命令**（两平台同一条）：

```bash
NEXFILM_DECODE_MATRIX_TAG=before cargo test --lib decode_matrix_diagnostic -- --ignored --nocapture
```

macOS 侧由负责人在 Mac 上跑同一条命令（tag 用 `before-macos`），产物回传后填 §2 的 macOS 列；跑不到的格子标「未验证」，不用推断值顶替。

## 3. 失败/Unresolved 清单（M3 验收清单）

1. **（Phase 3.1 更正）Phocus 导出 FFF 不属于 RAW 解码失败**（初版此条记为「双后端失败待上游修复」，撤回）。3 例（1 001-可以反相.fff / 无法反相.fff / 图像 001.fff）是 Flextight/Imacon 扫描仪容器：TIFF 头（`MM\0*`）+ 前置约 600 KB Phocus 设置段（IFD0 在偏移 600064）。应用分流 `is_scanner_fff_tiff` 识别容器本身（无 Imacon 字符串时按「渲染页 + 无相机 RAW 页」判定），从不把它们送进 RAW 后端。生产路径实测：**2/3 全幅解码成功**；`无法反相.fff` 的页 0 是 **659 MB 单条带**（5593×20597 RGB16），超过 `decode_scanner_fff_tiff_page` 给 tiff 解码器设的 512 MB 条带缓冲上限（`limits.decoding_buffer_size`），导出全幅与校准预览（都走页 0 全幅解码）对它报 `The Decoder limits are exceeded`——即该文件名字的由来，当年是旧的非流式读取整体超限，如今是流式页解码的单条带缓冲上限，性质未变：**应用级导入/导出失败，与 RAW 后端无关**。处置见 §7.3。
2. **nikon-zf-he**：等样本实测 M-HE 报错路径（#6 的彩条在 main 的 M-HE 合入后理论上已不再出现，需样本闭环）。
3. **hasselblad-x2d-3fr / nikon-zf-lossless**：等样本实测后填表。
4. 矩阵来源 Unresolved（identity）：当前 Windows 实测 **0 例**。

另：`1 001-FC导出tif格式导入失败.tif`（2026-03 负责人标注）走 profiled-TIFF 导入路径，不属 RAW 解码层（loose-TIFF 调查线已有结论），不入本矩阵，记录在案。

## 5. M3 方案（实现前落盘）

### 5.1 决策

- **统一版本：LibRaw 0.22.2-Release**，与 Windows rawlib 捆绑的完全同源。上游已发布 0.22.3，**不取**：Windows 侧 rawlib 没有 0.22.3 预编译库，追新意味着 Windows 也要换源码构建，破坏「Windows 字节级不动」这个 A/B 锚点。后续升级走既定机制（换 vendor 源码 → bump `RAW_DECODE_VERSION` → 跑解码 A/B）。
- **实现路径：macOS 侧 vendor 源码构建**。`vendor/rsraw-sys/` = rsraw-sys 0.1.1 的构建系统（cc 编译 LibRaw 源文件 + bindgen 现场生成绑定）+ LibRaw 0.22.2 上游源码树（tag 0.22.2）；`Cargo.toml` 的 macOS 目标依赖从 crates.io 的 `rsraw-sys = "0.1.1"` 改为 `path = "vendor/rsraw-sys"`。Windows/Linux 侧 rawlib 0.7.1 一行不动。
- **不引入 jpeg/lcms 外部依赖**（与 rsraw-sys 现状一致）：3FR/FFF 的无损 JPEG 由 LibRaw 内置 dcraw 解码器处理；应用缩略图路径不经 LibRaw 的 libjpeg 功能。此维度升级前后行为不变。

### 5.2 改动面

1. `vendor/rsraw-sys/`：LibRaw 0.22.2 源码（libraw/ 头文件、src/、internal/、LICENSE），build.rs 文件清单 = rsraw 0.1.1 清单 + 0.22.2 新增的 4 个源文件（`src/decoders/olympus14.cpp`、`src/decoders/pana8.cpp`、`src/decoders/sonycc.cpp`、`src/decompressors/losslessjpeg.cpp`），无删除项。
2. `Cargo.toml`：macOS 依赖指向 vendor 路径；`Cargo.lock` 相应更新（Windows 构建不编译该 crate，目标门控不变）。
3. `src/persistence.rs`：`RAW_DECODE_VERSION` 12 → 13。理由：macOS 解码输出（相机表/黑电平/颜色表）随 0.21.3→0.22.2 变化，必须失效旧代理/缓存；版本常量是全局 schema 值，不做平台分叉（分叉会造成同库内新旧混用）。Windows 侧输出不变，但同样付一次重解码——一次性成本，记录在案。
4. `src/raw_backend.rs` macos 模块：**零改动**。其 FFI 面只走稳定 C API 函数（`libraw_init/open_file/unpack/dcraw_process/make_mem_image/set_*/get_rgb_cam/...`，0.22.2 全部在位）+ bindgen 现场生成的结构体绑定；macos 模块读过的全部结构体字段（sizes/iparams/color/other 之 `raw_width…flip/filters/black/cblack/maximum/cam_mul/cam_xyz/linear_max/iso_speed/shutter` 等）已逐一对照 0.22.2 头文件静态核验存在。bindgen 在 HOST==TARGET 时现场生成，布局自动一致；crate 内 checked-in `src/bindings.rs`（0.21.3 时代）仅交叉编译回退用，已在 vendor README 标注。
5. M1/M2 回填逻辑：不动。新版本下 CFV/X2D 类机型矩阵来源从 `RawlerFallback` 变 `LibRaw` 是**预期变化**（值逐位相同，dual-source §9.4），A/B 只记录不报警。

### 5.3 风险面（0.21.3 → 0.22.2 行为变化）

- 相机表新增（X2D/X2D II、Z 8、Z 9、GFX 100 II 等）：macOS 侧矩阵来源与个别机型的黑电平/白电平读数可能变化——预期，A/B 逐条记录。
- 解码器修复/新增（olympus14、pana8、sonycc、losslessjpeg 拆分）：不影响已覆盖机型路径的既有行为（dcraw 主链未动），由矩阵 before/after 兜底。
- 结构体增量字段（`makernotes_cb`、`AspectRatio`、`linear_max[4]` 归位 colordata 等）：bindgen 现场生成，Rust 侧按名访问不受布局影响。
- **macOS 编译只能在 Mac 上验证**（本机 Windows 无 darwin 工具链）：vendor 就绪后由负责人跑 §1 命令即同时完成编译验证 + before-macos 矩阵回填。若构建受阻（bindgen/cc/源文件清单问题），按任务书约定交回架构对话，不现场改方案。

### 5.4 验收

- Windows：M3 前后矩阵 JSON 的 rows 逐字段一致（同 LibRaw 版本、零回归）；全量回归绿。
- macOS（负责人）：构建通过；before-macos vs after-macos 矩阵对比，逐条记录矩阵来源变化（RawlerFallback→LibRaw）与黑电平变化；旧库代理经 `RAW_DECODE_VERSION=13` 正确失效重建（打开旧项目不再用旧代理）。

## 6. 解码 A/B 报告（M3 后实测）

### 6.1 Windows（before `586fffa` → after `b1b322c`，同机实测）

- **矩阵对照**：`matrix-before.json` vs `matrix-after.json` 逐字段比对——**13/13 行完全一致**（10 个实测样本 + 3 个等待行）：解码成败、像素来源、矩阵值与来源、黑/白电平、色条判定全部不变；LibRaw 版本两侧同为 `0.22.2-Release`（Windows 走 rawlib，M3 不触碰）。**零回归、零新增 artifacts，符合"Windows 字节级不动"的设计预期。**
- **3 个 Phocus 导出 FFF 失败行**：升级前后行为一致（0.21.3→0.22.2 都没有该容器解析代码，M3 不承诺修复，见 §3.1 与 §7）。**更正（Phase 3.1）**：这批行重新归类为「不归 RAW 管辖的 Flextight 容器」，A/B 结论「零回归」本身不受影响。
- **旧库缓存失效实测**（`raw_decode_version_bump_invalidates_a_real_library`，副本上跑应用启动同一条 `init_schema`）：真实开发库 406 行全部 v12 → 迁移后全部 v13，渲染代理清除待重锚定，**零行残留旧代、零行丢失**。
- **"预览 = 导出"合同**：`export_preview_parity_diagnostic`（默认样张 0218-.tif）通过——L1 解码两链密度 R/G 一致到 0.0004，L3/L4 窗口映射差异在重测语义的既定范围内，L5 同态缩放两链 R/B 比一致到 0.003，L6 编码往返精确相等。合同在 M3 之后成立（解码层本次在 Windows 上零变化）。
