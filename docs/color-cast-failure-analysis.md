## 二、这次尝试做了什么

这轮改动是在 Phase 4 的基础上继续修改相机原生 RGB 路径，主要包含：

1. 删除片基的绝对上限 `FILM_BASE_MAX_DENSITY = 1.60` 和通道跨度上限 `FILM_BASE_MAX_CHANNEL_SPREAD`。
2. 相机原生路径不再逐通道归一化密度，而是用同一个亮度黑/白点把密度转回线性曝光：

```text
black = luma(d_min)
white = luma(d_max)
camera_positive[c] = (10^(density[c] - black) - 1) / (10^(white - black) - 1)
display_linear = camera_to_srgb * camera_positive
fit_linear_display(display_linear)
```

3. 对相机原生帧把 `analyze_proxy_density_limits` 的通道偏移固定为零。
4. 增加 `fit_linear_display_rgb`，在矩阵后做保持亮度的色域适配，替代逐通道硬钳制。
5. 把 `DENSITY_WINDOW_RULE_VERSION` 从 4 升到 5，旧帧会重新分析。
6. CPU、WebGL、代理和导出的顺序保持一致。

其中第 1 项是独立且必要的修正：欠曝会让整帧透射率下降，片基密度整体抬高，绝对上限确实会错误拒绝有效片基。第 2 项才是这次颜色回归的核心。

## 四、这次为什么会失败

### 4.1 同一个亮度白点不能代替逐通道的胶片响应

负片在相机原生 RGB 中的三个通道不是同一个曝光标量。片基、橙色色罩、染料吸收和相机光谱响应都会让每个通道在相同场景曝光下产生不同的密度端点：

```text
d_max = [0.665, 0.853, 1.020]   // _DSC7741
```

当前代码用 `luma(d_max)` 得到一个共享白点 `0.825`，然后把三个通道都除以同一个分母。于是三通道在“自己的 D-max”处得到的正片值并不相等：

| 样本 | d_max (R/G/B) | 共享白点 | 在各自 D-max 处的正片值 (R/G/B) |
|---|---:|---:|---:|
| `_DSC7732` | `0.654 / 0.790 / 0.930` | `0.771` | `0.717 / 1.053 / 1.534` |
| `_DSC7735` | `0.676 / 0.827 / 0.930` | `0.802` | `0.700 / 1.069 / 1.405` |
| `_DSC7741` | `0.665 / 0.853 / 1.020` | `0.825` | `0.638 / 1.078 / 1.665` |

这不是“白色略有偏差”，而是把蓝通道在白色处放大到红通道的 2.6 倍。相机矩阵随后把这个已经被破坏的通道比例解释成场景颜色，因此必然产生蓝/青或绿/青偏色。`fit_linear_display_rgb` 只能把超出色域的值向中性轴收缩，无法恢复已经被改写的通道比例。

### 4.2 旧路径并不完美，但它保留了逐通道响应

旧路径在密度域对每个通道分别做：

```text
normalized[c] = (density[c] - d_min[c]) / (d_max[c] - d_min[c])
```

它同样是用内容端点做归一化，不是真正的胶片特性曲线；它也有高光钳制和强色场景失真的风险。但它至少保留了“每个通道各自达到自己的 D-max”这一约束，所以在这三张正常负片上没有把中性白点直接推蓝。

这次尝试为了修正矩阵顺序，取消了这个逐通道约束，换成共享亮度尺度。结果是修好了一个理论问题（矩阵在线性域），却引入了更明显的颜色错误。**旧路径更好看，不等于旧路径就是正确答案；但它足以证明新路径不是可接受的替代。**

### 4.3 代码里已经记录过同类失败

`E:\Code\NegativeConverter\src\commands.rs:3047-3049` 的现有注释明确记录过共享尺度造成的后果：

```text
shared scale moved a Fujifilm RAF's neutral surface to B/G 1.599,
a Nikon NEF's to R/G 0.683, and a Noritsu JPEG's to R/G 0.692
```

这次改动在显示映射层重新引入了“共享尺度”，只是把密度域的共享窗口换成了线性曝光域的共享亮度黑白点。物理问题没有变：三个通道的胶片响应不同，不能用一个共享标量代替。

### 4.4 片基门限修复是必要的，但不是颜色修复

删除 `1.60 D` 上限解决了“欠曝时有效片基被拒绝”的问题。这在第三张的故障链里是真实缺陷，也是这次改动中应该保留的部分。

但片基门限只决定“有没有减掉正确的色罩”。减掉色罩之后，还要把每个通道的密度通过正确的胶片响应转成线性曝光，再应用相机矩阵。当前失败证明：**片基被接受、曝光不变性通过，仍然可以产生严重偏色。**

### 4.5 全局统计和 CPU/WebGL 一致性会掩盖错误

这次验证使用了：

- 全图均值、R/G、B/G、触顶比例；
- 正常曝光与 10× 欠曝输出一致；
- CPU/WebGL 最大通道差小于容差。

这些都不能证明颜色正确：

- 全图均值会把局部中性色偏移平均掉；
- 曝光不变性是一个数学恒等式，错误的通道映射同样可以保持不变；
- CPU/WebGL 一致性只证明两个后端执行了同一套错误公式；
- `fit_linear_display_rgb` 只处理矩阵后的越界值，不修复矩阵前的通道比例。

真正需要的是已知中性参考（灰卡、白卡、片头/片尾的已知区域）和逐通道胶片响应测量；没有这些参考，内容端点只能把某种场景误判成中性。

## 七、下一步的硬性方向

下一轮不要继续调窗口、偏移、亮度阈值或共享尺度。必须先补齐颜色模型：

1. **逐通道胶片响应。** 用已知曝光阶梯或校准色卡测量每个通道的密度到曝光关系，形成每通道的 `density -> linear exposure` 映射，而不是用全图内容端点代替。
2. **相机矩阵单独标定。** 在真实扫描光源、相机白平衡和镜头条件下标定 camera RGB 到线性 sRGB 的矩阵；不要把胶片响应误差混进矩阵。
3. **固定顺序。** 逐通道减片基 -> 逐通道特性曲线 -> 线性相机 RGB -> 相机矩阵 -> 显示色域/高光 -> 传递函数。
4. **验收必须用中性参考。** 至少要有灰卡/白卡或已知中性片基区域，检查矩阵前后三通道是否仍然相等；不能用全图均值或“蓝色更多”当作通过。
5. **最终验收仍以用户指定的问题照片为准。** 目标文件恢复后，左右 A/B 必须让新路径在已知中性区域和问题区域都不产生新的偏色；否则不接受。

这不是一个可以通过继续调启发式参数解决的问题。当前失败是结构性的，不是参数性的。
