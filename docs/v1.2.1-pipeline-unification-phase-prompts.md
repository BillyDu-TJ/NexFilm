# Nexfilm 1.2.1 管线统一：分阶段实施 Prompt

## 总体判断

只分 3 个阶段。核心是把“源文件进入密度阶段前必须输出什么”固定下来，而不是继续按文件后缀和调用入口分散打补丁。

- **Phase 1：统一输入契约与解码调度。** 解决相机 DNG、扫描仪 FFF、LinearRaw DNG、直接 RGB 的路径分叉，保证现代管线统一进入无界 f32。
- **Phase 2：统一片基与 Smart Auto 密度窗口。** 解决 ETTR 片基被拒、可疑片基被抵消、无片基时受限回退偏色的问题。
- **Phase 3：ICC/TIFF 元数据与解析加固。** 解决非标准 ICC、LinearRaw DNG 元数据、压缩/浮点 TIFF 和内存限制。

不建议再拆出“预览统一”“导出统一”“Roll 锚点统一”等独立阶段。它们必须和 Phase 1 的输入契约一起改，否则又会形成临时分支逻辑。

执行时按阶段逐个交付：同一个新分支上保留连续改动，每个阶段单独验收；上一阶段测试和真实素材检查通过后再开始下一阶段。不要为每个阶段再建分支，也不要在 Phase 1 尚未稳定时同时推进片基或 ICC 重构。

## Phase 1 Prompt：统一输入契约与解码调度

```text
执行 Phase 1：统一输入契约与解码调度。

背景：
当前 Nexfilm 的现代密度管线仍按后缀、相机类型和预览/导出入口选择不同解码函数。相机 DNG 被 smart_auto_working_basis 排除出 CameraNative；LinearRaw DNG 快速路径固定按 sRGB 解码；扫描仪 FFF 和绑定 Profile 路径仍经过 u16 sRGB；相机 DNG 的预览和导出还会走不同路径。这是当前最核心的预处理故障来源。

目标：
1. 在内部定义一个统一的“输入解码结果”契约，至少包含：
   - 未截断的 Rgb32FImage 工作像素。
   - WorkingBasis：CameraNative 或 ProPhotoEstimate。
   - 与实际解码一致的 InputDomainRecord。
   - 相机 RAW 可选的 camera_to_display 矩阵。
   - Capture Corrected 可选的 quality mask。
   类型名可以按现有风格确定，不要为了抽象而抽象。

2. 让所有现代路径消费同一个解码入口：
   - prepare_proxy / 画布预览。
   - 导出与批量导出。
   - Roll 锚点采样。
   - 接触印样。
   - 任何依赖 ProPhoto estimate 或 relative transmission proxy 的路径。
   不允许同一个文件因为入口不同而得到不同工作基、不同输入域或不同预处理。

3. 用文件元数据而不是扩展名区分 DNG：
   - Bayer/X-Trans 相机 DNG 进入 CameraNative。
   - 已渲染的 LinearRaw DNG 进入线性 ProPhoto f32。
   - 不能只用 !is_dng_extension(path) 决定。
   - 不能把所有 DNG 都当成 LinearRaw，也不能把所有 DNG 都当成相机 RAW。
   - 检测应读取 CFA/PhotometricInterpretation 等现有 TIFF 元数据；优先复用现有 read_classic_tiff_directory 和 DNG 相关辅助函数。

4. LinearRaw DNG：
   - 读内嵌 ICC。
   - 没有可用 ICC 时，明确使用 DNG ColorMatrix1 / AsShotNeutral 或现有明确的回退域。
   - 不允许在识别为 LinearRaw 后仍硬编码 ColorSpaceId::SRgb。
   - 修复 decode_uncompressed_linear_dng_reduced 只遍历 SubIFD、漏检 IFD0 的问题。
   - 保留大图快速解码能力，不要退化为无条件 image::open。

5. 扫描仪 FFF 和绑定扫描仪 Profile：
   - 输出 Rgb32FImage，不再返回 u16 sRGB 作为现代 Smart Auto 输入。
   - 保留现有 FFF 容器记录识别、扫描仪 ICC/Profile、Camera FFF 与 Scanner FFF 区分。
   - 不要重新把 Camera FFF 交给扫描仪 TIFF 分支。
   - 绑定 Scanner Profile 的路径也必须和未绑定路径使用同一个 f32 工作契约。

6. 现代路径绕过 compress_linear_srgb_for_density：
   - CameraNative 不经过该函数。
   - 直接 RGB / FFF / LinearRaw DNG 的 f32 ProPhoto 路径不经过 10% 色度地板。
   - 只做有限的正数边界处理，不能逐通道硬截断广色域。
   - 不要全局删除该函数；LegacyV1、兼容模式和仍需旧行为的路径应保持原样，先逐个确认调用点。

7. 统一预览和导出：
   - 同一个相机 DNG 在预览和导出中必须走同一工作基和同一色彩转换。
   - 导出可以有分辨率差异和可选的降噪，但不能因此改变输入域或相机矩阵的应用顺序。
   - 统一后仍要保留 f32bc17 对普通 TIFF/JPEG/PNG 的修复。

不在本 Phase 处理：
- 不修改 FILM_BASE_MIN_DENSITY、片基估计、Smart Auto 2%/98% 端点或 share_smart_auto_density_scale。
- 不引入新的完整 ICC 引擎；Phase 1 只要求不重复硬编码 sRGB，未知 ICC 的完整解析留给 Phase 3。
- 不重写 WebGL 渲染器、胶片曲线、曝光补偿或 UI。

测试要求：
1. 增加或更新相机 DNG 测试：确认进入 CameraNative，且预览/导出工作域一致。
2. 增加 LinearRaw DNG 测试：确认内嵌 ICC 被尊重；IFD0 主图通过 decode_uncompressed_linear_dng_reduced 解码成功。
3. 修正现有 linear_dng_round_trips_through_the_tiff_reader，不能直接绕过被测包装函数。
4. 扫描仪 FFF 测试：确认现代路径输出 f32，并保留容器声明的 Profile/Gamma。
5. 直接 RGB 回归：现有 f32bc17 的 TIFF/JPEG/PNG 测试必须继续通过。
6. 至少运行：
   - cargo fmt --all
   - cargo test --lib import_contract_tests
   - cargo test --lib 中包含 DNG、FFF、direct、decode 的测试
   - 如果时间允许，运行 cargo test --lib

验收标准：
- 现代管线中不再有“相机 DNG 预览走 u16、导出走 f32”的分叉。
- 现代管线中不再有“已识别 LinearRaw DNG 但固定按 sRGB 解释”的路径。
- Scanner FFF 和绑定 Profile 路径不再把 u16 sRGB 当作密度输入。
- 现有 CameraNative 和直接 RGB f32 修复没有回退。
- 所有输入类型的最终工作基和 input_domain 报告与实际解码一致。
```

## Phase 2 Prompt：统一片基与 Smart Auto 密度窗口

```text
执行 Phase 2：统一可信片基与 Smart Auto 密度窗口。

前置条件：
- Phase 1 已完成，输入解码已经统一为 f32 工作契约。
- 本 Phase 不再修改解码器、ICC/TIFF 解析或 UI。

背景：
当前 Smart Auto 会用同一片基偏移后的内容端点计算 d_min/d_max，片基在归一化公式中会被相减抵消。只吸片基、没有全曝光片头的局部 Roll 因此几乎看不到手动片基的作用。另一方面，0.02 D 下限和 0.98 采样线会拒绝 ETTR 亮片基；片基不可用时又容易进入 share_smart_auto_density_scale 的 ±0.20 D 受限回退，导致明显偏青蓝。

目标：
1. 明确区分三种状态：
   - TrustedBase：用户在片边采样或高置信度自动检测得到，可信作为中性黑场锚点。
   - ContentFallback：没有可信片基，只能用画面内容估计端点。
   - InvalidBase：检测到候选但证据不足，必须报告原因，不能静默当作有效片基。

2. 修复可信片基被内容窗口抵消：
   - 在 TrustedBase 路径中，净密度 D_net = D_raw - D_base 的黑场起点由片基锚定，不能让内容 2% 低端再次把片基偏移完全约掉。
   - 高端仍可来自内容高光分位点或完整 Roll 的 D_max，但低端不应无条件用内容 2% 分位点覆盖可信片基。
   - 保持中性色不偏，不得通过简单加一个全局通道偏置实现。
   - 这是会改变现有输出的改动，必须先用合成测试锁定数学，再用真实素材 A/B。

3. 修复无片基回退：
   - 不要继续把包含橙色色罩的绝对端点压到 ±0.20 D 后当成中性参考。
   - ContentFallback 默认应保留各通道自己的低端锚点，只共享或限制对比度跨度；具体方案以不产生单通道底噪爆炸、也不保留大面积色罩为准。
   - 将 share_smart_auto_density_scale 保留给 Legacy 或明确兼容路径，现代 Smart Auto 不应无条件调用它。
   - 没有可信片基时要明确报告 fallback，不要伪装成已中和。

4. 调整 ETTR/亮片基验证：
   - 不能只在 validate_film_base_candidate 中把 0.02 D 全局改成 0.001~0.002 D。
   - 片边带、Film Area 低密度尾部、画面内候选可以使用不同门限。
   - 放宽时必须同时要求样本数量、连续区域、与内容尾部一致，以及未达到真实硬件饱和。
   - 明确 0.98 与 0.995 的语义：0.98 是片基候选采样上限，0.995 是内容端点饱和排除线。不要为了“统一”而破坏各自用途。
   - 灯箱、片夹反光、开门和拼接白边不能被放宽后的门限误认成片基。

5. 保持完整 Roll 锚点语义：
   - 已有完整 Roll 片基和全曝光片头时，继续使用固定 Roll 映射。
   - 不要破坏 per-frame base offset 和 highlight fraction。
   - 现有 RollAnchored / CaptureCorrected / Legacy 分支必须保留。

不在本 Phase 处理：
- 不改解码器。
- 不重做胶片曲线、显示 gamma、3D LUT 或 WebGL。
- 不通过 UI 调参掩盖分析错误。

测试要求：
1. 新增合成测试：
   - 片基透射率 0.96、0.97、0.99 的 ETTR 案例，确认接受或明确拒绝的原因。
   - 只吸片基、没有全曝光片头时，修改片基必须改变最终输出。
   - 无边框、带橙罩的负片不能被 ±0.20 D 硬锁造成明显偏色。
   - 亮灯箱、开门、白边不会被误认成片基。
2. 保留并重新运行现有测试：
   - a_frame_keeps_its_own_co_sited_endpoints
   - complete_roll_anchors_* 
   - partial_roll_anchor_keeps_content_derived_display_limits
   - 与 Film base、ETTR、content limits、share scale 相关的全部单测
3. 真实素材 A/B：
   - 哈苏 FFF、尼康 NEF、Noritsu JPEG、LR 拼接 TIFF、无边框裁切样本。
   - 输出到 target/，不得写 test_picture/。
   - 记录中性面 R/G、B/G、黑场、高光和肤色变化；不能只用一个全图均值判断。

验收标准：
- 可信片基真正影响黑场和中和结果。
- ETTR 正常亮片基不再被 0.02 D 一刀切误杀，同时不把浅色背景当片基。
- 无片基路径不再必然产生大面积青蓝偏色，且不会把单通道底噪拉爆。
- 完整 Roll 固定映射与既有校准能力不回退。
- 现有正常素材没有肉眼可见的新偏色或黑位异常。
```

## Phase 3 Prompt：ICC/TIFF 元数据与解析加固

```text
执行 Phase 3：ICC/TIFF 元数据与解析加固。

前置条件：
- Phase 1 和 Phase 2 已完成。
- 本 Phase 只完善输入域解析和 TIFF 健壮性，不改变片基/密度数学。

目标：
1. 用真实 ICC 解析替代名称匹配：
   - 优先引入维护良好的 ICC 库，例如 moxcms、qcms 或兼容的 lcms2 封装。
   - 在引入依赖前检查许可证、平台构建和当前 Cargo 版本兼容性。
   - 解析 ICC 的 primaries、TRC/parametric curve、渲染意图和必要色适应。
   - 不能只靠 profile 名称识别；自定义扫描仪 ICC、ECI、Nikon、Hasselblad 和线性 ICC 都必须得到正确域。
   - 对未知 Profile，至少保留可用的原色域信息；不能用“未知即 sRGB”静默替代。

2. 保底处理：
   - resolve_direct_encoded_space 在识别不到名称时，仍然检查 ICC 是否声明线性 TRC。
   - 这只能避免二次 Gamma，不能代替完整 ICC 色彩转换。
   - 保持输入域状态栏显示与实际解码一致。

3. TIFF 解码：
   - 不要使用 tiff::decoder::Limits::unlimited() 去“修复” image::open；它不会修改 image 库的预算。
   - 使用当前版本对应的 `image::io::Reader` limits API（或升级后的等价入口），或直接走 `tiff` 解码器，并设置明确的可配置上限。
   - 保留大图流式解码；不要让所有压缩 TIFF 都退回全量 u16。
   - 对 DynamicImage::ImageRgb32F 保留 f32，不调用 into_rgb16。
   - 无 ICC 的 f32 TIFF 不能被一律视为线性；没有声明时按明确的未知/推断域处理。
   - 处理 Orientation 时保持预览、Film Area、裁切和导出几何一致。

4. LinearRaw DNG：
   - 优先使用内嵌 ICC。
   - 无 ICC 时按 DNG ColorMatrix1、AsShotNeutral 和现有 DNG 规范选择明确的回退域。
   - 不把相机 RAW 的 ColorMatrix 直接套到已渲染的 LinearRaw 数据上，除非代码和测试能证明语义正确。

5. 不破坏既有行为：
   - Phase 1 的 f32 输入契约继续有效。
   - Phase 2 的片基和 Smart Auto 窗口继续有效。
   - Legacy、CaptureCorrected、兼容模式不改。
   - 不修改 test_picture/。

测试要求：
1. 生成或使用小型合成 ICC：
   - 标准 sRGB。
   - 自定义线性 Profile。
   - 非标准描述名称但语义为 sRGB 的 Profile。
   - 未知原色但线性 TRC 的 Profile。
   - 至少一个矩阵型扫描仪 Profile。
2. TIFF：
   - 压缩 LZW/ZIP TIFF。
   - 分块 TIFF。
   - 32-bit float TIFF。
   - Orientation != 1 的预览/导出几何测试。
   - 超出限额时返回可读错误，不崩溃、不无界分配。
3. DNG：
   - LinearRaw DNG 内嵌 ICC。
   - 无 ICC、有 ColorMatrix1/AsShotNeutral。
   - IFD0 和 SubIFD 两种布局。
4. 运行：
   - cargo fmt --all
   - cargo test --lib
   - 与 TIFF/ICC/DNG 相关的 targeted tests

验收标准：
- 非标准 ICC 不再因为名称不匹配而被错误当成显示 sRGB。
- 自定义线性 ICC 不再被二次 Gamma。
- 大图压缩 TIFF 有明确上限和可读错误，不会因错误 API 而无界分配。
- f32 TIFF 的高光和类型不被无谓截断。
- DNG/ICC/TIFF 的输入域报告与实际像素处理一致。
```

## 阶段之间的验收边界

| 阶段 | 只应改变什么 | 不应改变什么 | 通过条件 |
| :--- | :--- | :--- | :--- |
| Phase 1 | 输入解码、DNG/FFF/Profile 路由、预览/导出一致性 | 片基阈值、密度窗口、UI、曲线 | 所有现代输入得到统一 f32 工作基，相机 DNG/FFF 不再有路径分叉 |
| Phase 2 | 片基可信度、ETTR 门限、无片基回退、端点锚定 | 解码器、ICC/TIFF 解析、渲染器 | 手动片基有效，ETTR 片基可用，无片基不产生固定偏色 |
| Phase 3 | ICC 解析、TIFF 限制/类型、DNG 元数据 | 片基与密度数学、既有渲染行为 | 非标准 ICC 和异常 TIFF 有正确域或明确错误 |

Phase 1 和 Phase 2 是 1.2.1 的核心收口工作。Phase 3 是格式健壮性加固，可以在前两阶段稳定后执行，但它不应再改变 Phase 1/2 已经确立的工作基和密度语义。
