## 二、阶段划分与顺序

```text
Phase 0  基线整理            ──┐
Phase 1  导出偏黄 诊断        │  ← 第一个 Prompt（本次下发）
Phase 2  导出偏黄 修复        │
Phase 3  解码失败：样本矩阵 + LibRaw 统一（M3）
         ── 打 tag：v1.2-clean-baseline ──
Phase 4  PR #10 代 rebase 与集成
Phase 5  反相偏色重新定基线（事项 1 分支的成果在新色彩基上重新评估）
Phase 6  v1.2 RC：全量回归 + 文档 + 发布
```

**排序理由**
1. **偏黄排第一**：它衡量的是"预览 = 导出"这条一致性合同。这条合同不成立的话，后面每一次反相 A/B 的肉眼判断都不可信。
2. **解码排在 PR 之前**：LibRaw 版本统一会改变所有 RAW 的解码输出（黑电平、颜色表）。PR #10 又会改变所有 RAW 的色彩基。两者都需要做全量 RAW A/B。先把解码定住，PR 的 A/B 只需做一次。Phase 1 也可能查到偏黄和平台 LibRaw 版本有关，这样 Phase 3 正好承接。
3. **PR 在干净基线上 rebase**：冲突只需要解决一次。

## 三、PR #10 的合并策略（代 rebase）

**做法：在我们的仓库建新分支，cherry-pick 作者的提交，提交作者署名保持不变。**

1. 从 `v1.2-clean-baseline` 建 `integrate/pr10-camera-native`。
2. `git fetch origin pull/10/head:pr10`，逐个 cherry-pick 三个提交（cherry-pick 默认保留 Author，我们是 Committer）：
   - patch 1（macOS 查找 Chrome）：main 已有等价改动 → 取并集或丢弃。
   - patch 2（诊断测试）：直接应用。
   - patch 3（主体）：预期冲突点见下表。
3. 冲突处理之外的补强单独提交，作者写我们自己，不混进作者的提交里。
4. 我们自己开一个新 PR（"Supersedes #10"），合并后在 #10 下留言致谢并关闭。如果作者的 fork 开了 "Allow edits by maintainers"，也可以直接 force-push 到他的分支，让 #10 本身被合并。二选一，**推荐前者**：不改写别人的分支，审查记录也更干净。

| 预期冲突/交互点 | 处理原则 |
|---|---|
| `ui/main.js` `loadProxyImage`：main 已改为"先存局部变量，通过守卫后一次性提交"，PR 在同一处新增 flag 8 和矩阵解析 | 矩阵也必须进入局部变量，和 domain/base/纹理**一起**原子提交；`currentPositiveToDisplay` 的初始值也要随 `currentProxyDomain=null` 的纪律处理 |
| `raw_backend` 双源分派：`camera_to_srgb` 可能来自 LibRaw、rawler 回填（M1）或 Unresolved | `camera_to_display` 永远不能持久化单位阵或 Unresolved 矩阵；M2（rawler 像素回退）路径同样走相机原生基 |
| `DENSITY_WINDOW_RULE_VERSION` | main=3 → PR 用 4。事项 1 分支的 4/5 从未发布，作废，不再复用 |
| `RAW_DECODE_VERSION`（main 已升到 12）、Phase 3 可能升到 13 | PR 不升 RAW_DECODE_VERSION（作者原意），保持不变 |
| PR 已知缺口 | 高光触顶的量化验收线；Roll 锚点因色彩基不一致被拒时给出 UI 提示；更新 `data_process_pipeline_doc.md` 和 `unified-density-pipeline.md` |
