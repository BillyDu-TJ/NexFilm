# 相机负片严重偏色：根因调查与失败记录（2026-11-12）

- 日期：2026-11-12
- 调查对象：`integrate/camera-native-rgb`（Phase 4 合并后）
- 结论状态：**失败，未解决。** 两个缺陷线索成立，但本文描述的 linear-positive 尝试在恢复负片上产生新的严重偏色；右侧为新路径，不能提交。

> **后验：本次尝试失败。** `*_old-new.jpg` 左侧是旧路径，右侧是当前新路径。恢复出来的负片显示右侧出现蓝/青、绿/青偏色，旧的共享尺度问题在“共享亮度黑白点”下重新出现。本文的“修复方案”部分仅作为失败设计记录，不是已验收方案。最新分析见 `docs/color-cast-failure-analysis.md`。

## 一、结论

这不是“欠曝文件本身有偏色”，也不是再调一次密度窗口能解决的问题。当前实现同时存在两处结构性错误：

1. **第三张的严重蓝偏，是相机原生密度基与 ProPhoto 基共用绝对片基阈值造成的。**
   欠曝使整帧透射率下降，密度整体抬高；相机的 as-shot 白平衡又只做通道衰减，因此片基密度可以远高于旧的 `1.60` 上限。有效片基被质量门拒绝后，算法退回“按画面内容猜通道平衡”，色罩重新进入正片，并产生接近上限的通道偏移。

2. **第四张的严重发白/褪色，是相机矩阵被放在逐通道密度归一化之后、并且矩阵输出被逐通道硬钳制造成的。**
   显示矩阵不再是线性 RGB 的色度变换，而是对三张已经各自拉伸过的单通道曲线做混合。矩阵的负系数会把彩色高光推到 `>1`，现有代码随即钳成白色；没有高光肩部，也没有色域映射。Phase 4 报告里的 `28.46%` 天空触顶就是同一缺陷的直接证据。

PR #10/#12 的主体方向是对的：它避免了“先套矩阵和色域压缩，再做负片 log”把蓝色抹平。但它只改变了矩阵的位置，没有同步改变密度分析、片基门限和显示端的高光处理。结果是旧问题从“蓝色被压成灰”变成了“蓝色被推爆、白色被洗掉”。

## 二、直接证据

### 2.1 欠曝 RAF：有效片基被绝对阈值拒绝

本机数据库里 `Capture One Catalog1949.raf` 的当前记录：

```json
{
  "base_source": "missing_film_base_reference",
  "fallback_reasons": [
    "missing_or_invalid_roll_anchors",
    "smart_auto_no_trusted_film_base",
    "film_base_out_of_range"
  ],
  "content_range": {
    "low":  [1.6821662, 1.9102520, 2.4492047],
    "high": [2.1981156, 2.5311353, 2.9899970]
  },
  "render_mapping": {
    "density_low":  [1.6082531, 1.8318774, 1.9970692],
    "density_high": [2.4082532, 2.6318774, 2.7970693],
    "channel_offsets": [-0.18881619, 0.034808233, 0.2]
  }
}
```

代码中的门限是：

- `src/commands.rs:2043`：`FILM_BASE_MAX_DENSITY = 1.60`
- `src/commands.rs:2055`：`validate_film_base_candidate`
- `src/commands.rs:2201`：候选失败后退回 `content_high_quantile`

这条路径的结果是：

1. 欠曝使整帧透射率下降，`-log10(T)` 整体上升；蓝通道内容低端已经到 `2.449 D`，明显超过 `1.60 D`。
2. 片基候选被判为 `film_base_out_of_range`，`base_density` 变成 `0`。
3. 色罩没有被逐通道减掉，随后 `share_smart_auto_density_scale` 用画面内容去猜通道中心，偏移到达 `[-0.189, +0.035, +0.200] D`，蓝通道已经撞到 `MAX_CHANNEL_OFFSET = 0.20`。
4. 最终画面大面积蓝偏，人物和地面失去原有颜色。

关键点是：**绝对密度阈值只在某个固定曝光缩放下成立**。把相机 RAW 的密度基从 ProPhoto 改成相机原生 RGB 后，同样的数字不再表示同一个物理位置；Phase 4 只 bump 了 `DENSITY_WINDOW_RULE_VERSION`，没有改任何片基绝对阈值。因此重新分析仍会再次拒绝这个有效片基。

`target/phase4-raw-ab/Capture One Catalog1949_A-R-C.jpg` 里 production / retired / camera-native 三份结果几乎一样蓝，也说明问题发生在三者共用的片基与窗口分析层，不在新旧矩阵顺序本身。诊断里的 `C_camera_native` 不能当独立参考，因为它复用了同一套错误的片基和端点。

### 2.2 4000363：高光在矩阵后被硬钳制

Phase 4 报告 `docs/v1.2-phase4-camera-native-rgb.md:147-152` 已经记录：

| 路径 | 天空 ROI 任一通道 ≥0.995 | ROI 均值 B/G |
|---|---:|---:|
| retired | 0.47% | 1.0297 |
| current | **28.46%** | **1.1268** |

报告把 `B/G > 1` 当成通过条件，但这是一个错误的验收指标：它奖励“把天空推蓝”，没有约束蓝色通道是否已经爆掉。天空 `B/G` 从 `1.03` 升到 `1.13` 的同时，触顶比例从 `0.47%` 升到 `28.46%`，这只能说明旧偏色被替换成了新的高光失真。

具体机制：

- WebGL 在 `ui/main.js:2540-2542` 先执行 `positive_linear = clamp(norm, 0, 1)`，再把逐通道归一化后的值送进 `u_positive_to_display`。
- CPU 在 `src/commands.rs:10910-10912` 做同一件事。
- `4000363.ARW` 的相机矩阵是：

```text
[ 1.7365, -0.5612, -0.1753 ]
[-0.1531,  1.5584, -0.4053 ]
[ 0.0199, -0.4041,  1.3842 ]
```

矩阵三行之和都是 `1.0`，所以输入 `(1,1,1)` 时中性色仍会保持中性。但它的对角线最大到 `1.7365`，负系数会放大单个彩色通道：当蓝通道归一化到 `1.0`、红绿较低时，蓝输出可以超过 `1.0`。当前代码没有留高光余量，矩阵后直接钳制，于是蓝天空和白色大教堂同时贴顶，细节和色度一起丢失。

换句话说：

- 旧路径的 gamut compression 在负片反相之前把蓝压平，天空变灰；
- 新路径取消前置压缩后，蓝被恢复，却在显示端被矩阵放大到爆掉；
- 两者都不是正确的颜色管理。

### 2.3 一个更基础的问题：矩阵和逐通道窗口不可交换

相机矩阵是线性 RGB 之间的 3×3 变换，必须作用在线性光值上。当前实现却先做：

```text
D_camera -> 每通道各自的 D_min/D_max 仿射归一化 -> 3×3 相机矩阵 -> 钳制
```

不同通道的仿射参数不同，因此矩阵混合的不是“同一曝光尺度的 RGB”，而是“已经分别拉伸过的三个标量”。矩阵的行和就算为 1，也不能保证中性轴、色相和高光不漂移。正常样张有时看起来“还行”，只是该场景的通道端点恰巧接近；欠曝和强色场景会把误差放大。

相关位置：

- `src/commands.rs:3001-3070`：有片基时保留逐通道自己的 `D_min/D_max`。
- `src/commands.rs:10724-10730`：选择相机矩阵或 ProPhoto→sRGB。
- `ui/main.js:2538-2542`：归一化后套矩阵。
- `src/commands.rs:10910-10912`：CPU 同路径。

## 三、为什么之前的尝试一直没解决

| 时间/分支 | 做的事 | 为什么没有解决 |
|---|---|---|
| `9819b59`（2026-08） | 用 f32 套相机矩阵，并在 log 前做 `compress_linear_srgb_for_density`，避免 16-bit 有符号截断 | 负片橙色色罩的蓝通道本来极小；以亮度 10% 为底的 gamut compression 把真实的蓝色信息改写成了统一的底噪。于是天空、湖水呈灰绿/青色。治的是“矩阵输出不能直接进 u16”，不是负片的反相基。 |
| `ccb23e3` / 统一密度管线 | 片基扣除后，改回逐通道同像素端点，修复共享窗口造成的尼康偏绿、富士 RAF 偏紫 | 这解决了某些样张的端点比例，但仍把逐通道端点当作颜色校正。每个场景自行决定通道缩放，遇到欠曝和大幅色罩时会把内容差异误认成印片响应。 |
| `codex/prescribed-response-fallback` / `9c9d332` | 2383 印片曲线、逐亮度档 normalizer、跨度均衡 | 逐通道印片曲线会旋转色相；改成只映射亮度后，又需要从画面内容推断中性，无法区分“场景本身是蓝色”与“蓝偏”。跨度均衡实验直接把整批画面变薄荷绿。该分支被放弃，原因记录在 `docs/unified-density-pipeline.md`。 |
| PR #10/#12 / Phase 4 | 相机 RAW 在 camera-native RGB 中做密度，矩阵随正片显示 | 方向上解决了前置矩阵/压缩破坏蓝色的问题，但没有同步重做片基门限、逐通道归一化和显示端色域管理。结果是把旧的“蓝色被压平”换成了新的“蓝色被放大后钳白”。 |

四轮尝试有一个共同点：都在**用画面内容推断缺失的颜色参考**。片基、逐通道端点、灰世界偏移、逐亮度档 normalizer 都不是中性参考；没有色卡、没有已知光源、没有胶片响应曲线时，它们只能把某一种内容误判为偏色。解决方向必须是增加可验证的物理或标定参考，而不是继续调启发式参数。

## 四、本次尝试（已失败）

这次尝试曾计划在一个提交中完成，不拆阶段。核心是把相机 RAW 的“颜色变换”和“曝光/色调映射”分开：

```text
相机线性透射值
  -> 逐通道减片基，得到相对于片片的 log 密度
  -> 用同一个亮度黑/白点转回线性曝光
  -> 在线性 RGB 域应用相机矩阵
  -> 保持亮度轴的色域适配 + 高光余量
  -> sRGB 显示传递
  -> 现有 Tone Curve / Aesthetics
```

具体落地（以下设计已被 A/B 结果否定，保留用于复盘）：

1. **片基验证去掉了与曝光绑定的绝对上限。**
   `FILM_BASE_MAX_DENSITY` 和 `FILM_BASE_MAX_CHANNEL_SPREAD` 被删除；剩余门限只检查样本数、有限值和“片基必须是可见透射”。
   片基是相对参考，欠曝只会让有效片基在数值上整体变大，不能再因此拒绝它。

2. **相机 RAW 的矩阵改为作用在线性曝光上。**
   密度先按片基相对化，再用同一个标量黑/白点转回线性曝光；三通道共享这个曝光尺度，不再先各自拉伸 D-min/D-max 再混合。

3. **矩阵后的高光不再逐通道硬钳制。**
   新增保持亮度的色域适配：负值向中性轴收缩，超过 1 的彩色高光按色度收缩而不是把三个通道一起推成 255。随后才做 sRGB 显示编码。

4. **相机原生的分析不再用画面内容猜通道平衡。**
   `analyze_proxy_density_limits` 对 camera-native 通道偏移固定为 `[0,0,0]`，只保留测量到的内容端点用于亮度黑/白点。

5. **WebGL、CPU 预览、缩略图和导出共用同一顺序。**
   相机矩阵由 proxy header flag 8 和 `u_camera_native_display` 传入；`DENSITY_WINDOW_RULE_VERSION` 从 4 升到 5，旧帧会重新分析。

## 五、自动验证（不能证明颜色正确）

已完成的自动验证：

- `cargo test --lib`：314 passed / 0 failed / 28 ignored。
- `node --test ui/*.test.js`：19 passed / 0 failed。
- `node scripts/verify-webgl-shaders.cjs`：4 个 WebGL 程序编译链接通过。
- `cargo test --lib cpu_render_fixture_for_webgl_parity -- --ignored` + `node scripts/diagnose-cpu-webgl-parity.cjs`：CPU/WebGL 最大通道差 `0.0036`，低于 `0.02` 容差。
- `cargo fmt --all -- --check`：通过。

新增的回归断言：

- 欠曝只改变整帧密度偏移时，camera-native 输出保持不变。
- 线性高光经过矩阵和色域适配后落在 `[0,1]`，且不会三通道全部贴白。
- 高片基密度 `[2.3, 2.6, 2.9]` 可通过片基门限。

真实 RAW 曝光缩放验证（`G:\DCIM\755ND810\_DSC7500.NEF`）：

| 输入 | 片基门限 | 当前旧路径 | 新路径 |
|---|---|---|---|
| 正常曝光 | 接受 | 正常基线 | 中性建筑与蓝天保持，高光有肩部 |
| 人工压低 10 倍曝光（模拟欠曝） | **接受**（片基 `1.54/1.63/1.69 D`） | 旧分析把有效片基判为超出绝对范围，转去内容窗口 | 统计与观感与正常曝光一致 |

这些检查只证明片基门限、曝光不变性和 CPU/WebGL 一致性；它们不能证明颜色正确。恢复负片上的右侧偏色已经证明：即使这些检查通过，错误的逐通道映射仍然可以把正常画面改坏。`fit_linear_display_rgb` 也无法修复矩阵前的通道比例错误。

后验补充：上表只针对 `_DSC7500.NEF` 的曝光缩放，不是对全部负片的颜色验收。2026-11-12 用恢复出来的 `_DSC7732/_DSC7735/_DSC7741` 做同尺寸 A/B 后，新路径右侧出现新的蓝/青、绿/青偏色，说明“观感与正常曝光一致”不能推导为“颜色正确”。本实验已失败，不能提交。
